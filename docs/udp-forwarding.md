# UDP 大报文完整性修复

此前面板生成的 UDP listener 只包含 `keepAlive: true`，节点使用默认的
8192 字节接收缓冲区。单个 UDP 报文超过此值时，读取操作会截断报文；
例如发送 9000 字节，转发目标只收到 8192 字节。

面板现在为新建、更新的转发显式下发以下监听器参数，端口转发和隧道转发共用：

```yaml
listener:
  type: udp
  metadata:
    keepAlive: true
    readBufferSize: "65536"
```

节点的默认接收缓冲区也调整为 65536 字节，可覆盖普通 IPv4/IPv6 UDP 报文。
字符串形式的显式 `readBufferSize` 配置仍有优先级。

这里使用字符串是为了兼容旧节点：JSON 数值被解码为 `float64` 后，旧版的
整数 metadata 读取工具会忽略它，退回到默认值；字符串 `"65536"` 可以正常
解析。面板下发和手工编辑 JSON 配置时都应保留引号。

## 排队内存优化

监听器保留完整报文的接收能力，小报文入队时复制到匹配实际长度的缓冲池档位，
接收缓冲区继续复用。如果报文已经需要当前的大缓冲区档位，则直接移交缓冲区，
避免一次没有内存收益的复制。

以 64 KiB 接收缓冲区为例，单个排队报文持有的底层数组容量为：

| 报文长度 | 优化前 | 优化后 |
| --- | --- | --- |
| 64 字节 | 64 KiB | 128 字节 |
| 1200 字节 | 64 KiB | 2 KiB |
| 9000 字节 | 64 KiB | 16 KiB |
| 65507 字节 | 64 KiB | 64 KiB |

因此，1200 字节报文排满一个 128 包的客户端队列时，排队缓冲区从约 8 MiB
降至 256 KiB。32 个客户端全部排满时，从约 256 MiB 降至 8 MiB。
这些数字只计算排队报文的底层数组，不包含连接、接收缓冲区和运行时开销。

队列已满时直接丢弃当前报文，避免继续分配、复制；连接关闭时归还未消费的
缓冲区，并阻止关闭后继续入队。监听器关闭会等待接收循环退出，再清理客户端，
覆盖关闭与接收同时发生的情况。归还缓冲池用于后续复用，不代表进程 RSS
立即下降。

该方案给需要缩小存储的小报文增加一次内存复制，性能应通过实际工作负载评估。

## 已有部署如何生效

- 更新面板后，新建、编辑保存或后台重新下发的转发使用显式的 64 KiB 配置。
  旧版节点本身支持此参数，因此能处理面板下发的新配置。
- 更新节点并重启后，原有未配置 `readBufferSize` 的转发会使用新的 64 KiB
  默认值，无需删除重建转发。节点安装脚本的更新流程会重启节点服务。
- 仅更新面板不会自动修改已经运行的节点监听器。推荐面板和节点一起升级。
- 手工设置过较小 `readBufferSize` 的节点配置需要单独调整。重启节点或重新
  下发服务会重建相关连接，应安排合适的升级时间。

## 验证

节点回归测试通过真实的本地 UDP 套接字，对未设置缓冲区的旧配置与显式
64 KiB 配置检查报文边界和逐字节完整性，包含 8192、8193、9000 字节。
Linux 下还检查 65507 字节的 IPv4 UDP 有效载荷。

```bash
cd go-gost/x
go test ./listener/udp -run TestListenerPreservesLargeDatagrams -count=1
```

内部队列测试覆盖空报文、大报文、缓冲区复用、满队列、32 个积压客户端，
以及读写和关闭并发。基准测试使用内存中的报文源，衡量本地队列处理开销，
不代表公网吞吐量。

```bash
cd go-gost/x
go test -race ./internal/net/udp ./listener/udp
go test ./internal/net/udp -run '^$' -bench BenchmarkListenerReceive -benchmem -cpu=1
```

本地验证记录（2026-09-07）：

- 队列和 UDP listener 的 `go test -race` 通过，Go 模块测试和 `go vet` 通过。
- 用编译后的节点程序测试单节点转发、TCP 隧道、TLS 多跳，18 项报文完整性
  检查通过；每种模式还完成 64 个客户端各 50 次、每包 1200 字节的收发，
  合计 9600 次检查未发生超时或内容不匹配。
- 内存报文源的基准测试在 Apple M4、Go 1.26.5、单个 Go 逻辑处理器下运行，
  下表为 5 次运行的中位数。基线已采用 64 KiB 接收容量，仍使用原始排队逻辑。

| 报文长度 | 原始排队逻辑 | 优化后 | 单次处理耗时变化 |
| --- | --- | --- | --- |
| 64 字节 | 377.9 ns | 358.8 ns | -5.1% |
| 1200 字节 | 395.6 ns | 392.1 ns | -0.9% |
| 9000 字节 | 571.8 ns | 624.5 ns | +9.2% |
| 65507 字节 | 2199 ns | 2340 ns | +6.4% |

该基准只反映本地队列处理路径，存在机器和调度差异。内存占用改善有明确的
容量约束，CPU 开销仍取决于报文大小和实际负载。

后端 `GostUtilTest` 检查端口转发和隧道转发的新建、更新命令均包含此参数。

```bash
cd springboot-backend
mvn test -Dtest=GostUtilTest
```

该修复针对接收缓冲区造成的报文截断。当前面板的诊断仍使用 TCP 探测，
不能用其结果确认 UDP 可达性；公网丢包、限速和长期高负载需要在真实环境验证。
